# migiude: AI 開発フロー

ユーザーと AI が一緒に開発するときの進め方。過去の数百セッションで繰り返し出た指摘から作った。
**フローの各段階に、守らないとやり直しになる理由が付いている。** 迷ったら理由のほうで判断する。

## 0. 受付と分類

最初に依頼を次のどれかに分類し、対応する reference を読む。複数にまたがる場合は主になるものから始める。

| 種類 | 例 | 読むもの |
|---|---|---|
| 実装 | 機能追加、修正、リファクタ、バージョンアップ | [references/implement.md](references/implement.md) |
| レビュー | 自分の PR への指摘対応 | [references/review.md](references/review.md) |
| 設計・文書 | 設計相談、仕様書、実装計画 | [references/design-docs.md](references/design-docs.md) |

**開発・実装は監督モードで進める。** 実装、およびそのための設計に入るときは、規模にかかわらず [references/orchestrate.md](references/orchestrate.md) に従う。この場合、起動元のセッションは監督役になり、設計・レビュー・実装をそれぞれサブエージェントに割り振る。各サブエージェントは、担当するステップに合う reference（設計なら design-docs.md、実装なら implement.md、レビューなら review.md）に従う。

成果物に文章（コード中のコメント、コミット、PR 本文、文書、レポート）が含まれるときは [references/writing.md](references/writing.md) も読む。

**依頼の「目的」を一文で言い直してから始める。** 「失敗しているかを知りたい」のか「設定値を知りたい」のかを取り違えると、作業がまるごと無駄になる。曖昧なら、着手前に一つだけ聞く。

目的が定まったら、利用中のツールの改名機能で、現在のセッションに開発対象と作業内容が分かる短い日本語名を付ける（例「ログイン時の二重送信を修正」）。

## 1. 裏取り（推測しない）

- 判断の根拠は一次情報から取る。優先順は **実コード（file:line） > 実データ・実際の実行結果 > 公式ドキュメント > 既存の他の実装** の順。記憶や一般論で埋めない。
- 「〜のはず」「おそらく」で次の段階に進まない。確かめられないなら「未確認」と明記し、確かめる方法を添える。
- 存在するか分からないもの（ホスト名、権限名、オプション、API）を挙げない。挙げる前に存在を確認する。
- 似た処理がすでにあるなら、まず「他の箇所ではどう実装しているか」を見て合わせる。

## 2. 方針提示

- ユーザーに選んでもらう論点は、選択肢に記号（A/B/C）を振り、推奨と理由を添える。
- 設計とレビューの中で方針が分かれたときは、ユーザーの選択を待たずに推奨する案で進め、選んだ案と理由を伝える。レビューの指摘は medium 以上だけを直す（どちらも [references/orchestrate.md](references/orchestrate.md) の「指摘の重さと対応」「方針が分かれたとき」）。
- 要件を変える判断は [references/orchestrate.md](references/orchestrate.md) の「要件を変える判断の基準」に従う。
- 依頼の範囲は広げない。関連して気づいた改善・別件は今回の変更に含めず、「[本筋以外の発見](#本筋以外の発見)」に従ってタスクとして起票する。勝手に実装しない。
- 「実装はしないで」「まだ更新しないで」「やり方だけ」と言われたら、その範囲を厳守する。

## 3. 準備

- 作業は main/master に直接せず、タスクごとにブランチ（可能なら worktree）を切る。**切り忘れはよくある指摘**なので、最初の編集の前に必ず確認する。
- 派生元を確認する。「今いるブランチ」から切ってよいとは限らない。原則は `git fetch` してから `origin/<デフォルトブランチ>` から切る。ローカルのデフォルトブランチは古いことがあるので、比較の基準にも使わない。
- ブランチ名は [Conventional Branch](https://conventionalbranch.org) に従い、`<type>/<description>` の形で英語で付ける。type は `feature/`（`feat/`）、`bugfix/`（`fix/`）、`hotfix/`、`release/`、`chore/` から選ぶ。description は小文字の英数字とハイフンで、内容が分かる短い名前にする。issue があれば `feat/issue-123-add-login` のように番号を入れる。
- 最初の編集前に、セッションに割り当て済みのブランチと worktree の名前も確認する。このタスク用のローカルブランチ名が上の規則や作業内容に合わなければ改名する。detached HEAD なら、派生元を確認して規則どおりのブランチを作る。既存の PR に対応するときは、その PR のブランチを使う。
- タスク用 worktree の名前はブランチの `<description>` に揃え、割り当て済みの名前が異なれば変更する。ツールが管理する worktree はそのツールの表示名を変更し、管理用パスは維持する。改名機能がない場合は、その旨を伝える。

## 4. 実行

各 reference の手順に従う。どの種類でも共通して守ること:

- **最小スコープ**: 頼まれた分だけ変更する。ついでのリファクタ、頼まれていない CI・監視・ログ出力・設定の追加はしない。
- **既存の流儀に合わせる**: 命名、ディレクトリ構成、コメントの量、エラー処理、ライブラリの選び方を周囲のコードに揃える。
- **単純に保つ**: 応急処置や一時対応なら素直なベタ書きでよい。抽象化・変数化・汎用化は求められてから。
- **根本原因を直す**: 回避策（とりあえず動く設定、余計な環境変数、広い権限）で済ませる前に、なぜそうなるのかを調べる。回避策を採るなら、回避策であることと根本対応の候補を明記する。
- **テストのために実装を歪めない**。権限・スコープは最小で考える。
- **開発の仕組みとプロダクトを混ぜない**: AI 用のハーネスや一時スクリプトに依存した名前・コードをプロダクトのリポジトリに入れない。
- **書く場所を間違えない**: 仕様は仕様書に、理由はコメントやコミットに、個人の好みは個人設定に書く。組織で共有するファイルに個人ルールを入れない。

## 5. 自己検証

- 「できました」の前に、**自分で実行して結果を示す**。lint、型チェック、該当するテスト、ビルド、実際の起動や curl。実行していない検証を「確認済み」と書かない。
- 実行環境が指定されているなら（コンテナ内、特定のステージングなど）その環境で実行する。ホストで代用したなら代用したと書く。
- UI の変更は、可能ならブラウザやスクリーンショットで確かめる。
- 検証できなかった項目は「未検証」として理由と確認方法を残す。

## 6. 締め

- **明示の指示を待つ操作**: 既存 PR の本文などの手動更新、外部文書（Wiki、チケット、チャット）への投稿や更新、マージ、デプロイ。ただし「[本筋以外の発見](#本筋以外の発見)」によるチケットの新規起票は、指示を待たずに行う。
- コミットは**意味の単位に分ける**。量が多いときは先に「どのファイルをどのコミットにするか」の計画を挙げて承認を得る。今回の依頼に含まれる変更だけをコミットする。
- コミットメッセージは [Conventional Commits](https://www.conventionalcommits.org) に従う。type は英語、タイトルと本文は日本語で書く（[references/writing.md](references/writing.md)）。PR 本文の形式は、リポジトリの既存の PR とテンプレートに合わせる。
- 実装・修正は、自己検証と差分のセルフレビューを終えたら、明示の指示を待たずに作業ブランチを push し、PR を作成する。既存 PR の対応では、そのブランチに push する。続けて CI を確認し、指摘に対応する。詳細は [references/review.md](references/review.md)。
- 取り消しには履歴を書き換える操作（rebase、force push）より revert を優先する。履歴を書き換える必要があるならユーザーに確認する。

## 7. 片付けと引き継ぎ

- 作業中に見つけた本筋以外の論点は、その場で深追いせず、「[本筋以外の発見](#本筋以外の発見)」に従って起票する。
- マージ後は、確認せずに不要になったブランチ・worktree を畳み、ローカルのデフォルトブランチを最新化する（残すものの条件は [references/orchestrate.md](references/orchestrate.md) の「PR と片付け」）。
- セッションが長くなった、または独立した作業が出てきたら、別セッション（あるいはサブエージェント）に切り出す。切り出すときは背景・対象ファイル・完了条件を書いて渡す（書き方は [references/orchestrate.md](references/orchestrate.md) の「ブリーフに書くこと」）。

## 本筋以外の発見

設計・実装・レビュー（セルフレビュー、レビューエージェント、人のレビュー）の途中で、今回の目的や完了条件には含まれないが対応する価値のある点が見つかることがある。たとえばリファクタリング、既存の不具合、テストの不足、古くなった文書や依存。

- **今回の変更には含めず、見逃しもしない**: 見つけたその場でタスクとして起票する。作業の終わりにまとめようとすると、忘れるか、根拠の文脈が消える。
- **本筋か別件かは完了条件で決める**: 今回の目的を満たすのに必要なら本筋として直す。不要なら別件にする。迷ったら [references/orchestrate.md](references/orchestrate.md) の「要件を変える判断の基準」に照らす。
- **起票するのは根拠を示せるものだけ**: 表記や好みの範囲（重さが low 相当）は起票しない。
- **起票先と書き方はリポジトリ・プロジェクトに従う**: GitHub の issue か、Jira などのチケットか、どんな粒度・タイトル・ラベルで切るかはプロジェクトごとに違う。次の順で確かめ、定めに従う。
  1. リポジトリのエージェント向けの指示ファイル（`CLAUDE.md`、`AGENTS.md` など）
  2. `CONTRIBUTING.md` などの開発ガイドと、issue テンプレート（`.github/ISSUE_TEMPLATE/` など）
  3. 既存のチケットの書き方（タイトルの形式、ラベル、粒度）
- **起票の前に重複を確かめる**: 起票先で既存のチケットを検索する。同じ内容があれば新規に作らず、そのチケットを報告する（既存チケットへのコメントは明示の指示を待つ）。
- **本文に書くこと**: 何が問題か、根拠（file:line、実行結果）、見つけた作業（PR や issue へのリンク）、直し方の案。優先度・担当・期限などの割り当ては、プロジェクトに定めがなければ設定せず、ユーザーに任せる。文章の作法は [references/writing.md](references/writing.md) に従う。
- **起票先が決められないときは推測しない**: 指示ファイルなどに定めがなく起票先が分からない、起票の手段や権限がない、プロジェクトが AI による起票を禁じている、のいずれかなら起票しない。起票文案をまとめてユーザーに渡し、起票先を聞く。
- **起票したら伝える**: 起票したチケットの URL を、そのステップの報告に一覧で添える。
- 監督モードでは、サブエージェントは起票しない。別件として報告させ、監督役が起票する（[references/orchestrate.md](references/orchestrate.md)）。

## 常に守る原則

- **日本語で、常体で書く**。チャットの返答、レポート、レビュー結果、コミット一覧、コード中のコメントも含む（リポジトリが英語の慣習なら、コード中のコメントだけはそれに合わせる）。
- **状況を常に見える状態に保つ**: いま何をしているか、何が起きているか、次にユーザーがすべきこと（実行してほしいコマンド、判断してほしい点）を短く示す。「何をすればいい？」「今何を調べてる？」と聞かれたら説明が足りていない。
- **確認しすぎない**: 承認済みの範囲では自走する。確認が必要な場面は「方針提示」と「締め」に従う。
- **人と AI の分担を明示する**: 認証・ログイン、本番データへのアクセス、破壊的な操作、課金が発生する操作はユーザーに任せる。そのためのコマンドやクエリは、プレースホルダーまで埋めてコピペで動く形で渡す。AI 側では、読み取り操作と「締め」で定めた手順に沿う外部操作を実行する。
- **秘密情報を扱わない・残さない**: `.env` 等の秘密ファイルを読まない。トークンや個人情報をコード、ログ、文書、コミット履歴に残さない。
- **重い設計には独立した反証を入れる**: 設計案は、別のエージェントやセッションに「反証する立場」で検証させてから確定する。監督モードのレビューと独立レビューがこれに当たる（[references/orchestrate.md](references/orchestrate.md)）。単純な質問には使わない（コストに見合わない）。
- **ユーザーの反論には根拠で答える**: 「それ本当？」「なぜ？」と聞かれたら、根拠を示すか、確かめ直して誤りなら認めて直す。押し切らない。
- **指摘を受けたら**: 何が違ったかを一行で認め（言い訳を重ねない）、直す。同じセッション内で同種の箇所が他にないかを確認し、あれば一緒に直す。今後も繰り返しそうな指摘なら、ユーザーの個人メモリや設定に残すかを提案する。
