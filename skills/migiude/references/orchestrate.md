# 監督モード（サブエージェントに割り振って進める）

開発・実装は、規模にかかわらずこの進め方で進める。起動元のセッションは**監督役**になる。自分では設計も実装もせず、各ステップをサブエージェントに割り振る。

各ステップを別のエージェントにする理由は 2 つ。1 つは、設計した本人がレビューすると自分の前提を疑えないこと。もう 1 つは、監督役が手を動かすと、全体の進み具合とユーザーの判断待ちが見えなくなること。

## サブエージェントを使う理由

- **結果が全文で戻る**: サブエージェントの最終報告は、監督役にそのまま返る。
- **ユーザーとの窓口が 1 つになる**: サブエージェントはユーザーに直接聞けない。質問は監督役に返り、監督役が自分で決めるか、ユーザーに聞くかを振り分ける。ユーザーが複数のセッションを行き来して答える必要がなくなる。また、ユーザーが別セッションで直接やりとりしたせいで、監督役が知らないうちに状況が変わる、ということも起きない。
- **続きを頼める**: 同じサブエージェントに続きを頼めば、それまでの文脈を保ったまま作業を再開できる。エージェントに続きを頼む手段がない場合は、新しいサブエージェントを立て、前の成果物のパスとそれまでの経緯をブリーフに書いて渡す。

別セッションを使うのは、次の場合に限る。
- ユーザーがその作業を自分で開いて、見たり口を出したりしたいと言った場合。
- 本筋とは別の作業を切り出す場合（途中で見つかった既存の不具合の調査など）。

## 流れ

| # | ステップ | 担当 | 次へ進む条件 |
|---|---|---|---|
| 1 | 設計 | 設計エージェント | 設計書ができた |
| 2 | 設計レビュー | レビューエージェント | 判定が OK。要修正なら 1 に戻す（r2, r3, …） |
| 3 | 独立レビュー | 新しいレビューエージェント | 判定が OK。要修正なら 1 に戻し、このレビュアーに再レビューさせる |
| 4 | 実装 | 実装エージェント（専用の worktree） | 作業単位でコミットし、検証が済んだ |
| 5 | 実装レビュー | 新しいレビューエージェント | 判定が OK。指摘を直すなら 4 のエージェントに追加のコミットを積ませる |
| 6 | push・PR 作成 | 監督役 | 作業ブランチを push し、対応する PR があることと CI の結果を確認した |
| 7 | 片付け | 監督役 | マージ後 |

- 1 と 2 を往復するときは、同じ設計エージェントと同じレビューエージェントに続きを頼む。新しく立て直すと、それまでの経緯を渡し直すことになる。
- 3 と 5 は、必ず新しいエージェントを立てる。前のステップの文脈を持たないことに意味がある。
- サブエージェントを裏で動かせるなら、裏で動かす。終わったことが知らされる仕組みがあるなら、状態を何度も問い合わせない。待っている間は、ユーザーに今の状況を伝える。

- 1〜3 では、合意済みの要件の範囲で設計とレビューを進める。ユーザーの判断が必要な点は「方針が分かれたとき」に従う。
- **実装開始**: 実装を含む依頼では、設計レビューと独立レビューがともに OK になったら、採用した設計と理由を伝え、そのまま実装エージェントに着手させる。
- 5 の指摘は「指摘の重さと対応」に従って扱う。実装レビューで OK が出たら、SKILL.md の「締め」に従い 6（push・PR 作成）へ進む。

## 指摘の重さと対応

設計レビュー、独立レビュー、実装レビューの指摘には、次の 3 段階の重さを付ける。

| 重さ | 目安 | 対応 |
|---|---|---|
| high | 直さないと動かない、壊れる、issue の完了条件を満たさない、データやセキュリティを損なう | 直す |
| medium | 動くが、不具合や保守の負担につながるおそれが高い（テストの抜け、設計との食い違い、エラーの扱いの漏れなど） | 直す |
| low | 表記、命名、好みの範囲の改善、起きる見込みの低い懸念 | 直さない |

- **本筋か別件かを分ける**: 指摘には、重さとは別に「本筋」か「別件」（今回の目的・完了条件に含まれない改善や問題）かを付けさせる。別件は判定に数えず、今回は直さない。監督役が SKILL.md の「本筋以外の発見」に従って、その場で起票する。
- **判定**: 本筋の指摘に medium 以上が 1 つでもあれば要修正、low だけなら OK にする。
- **直すかどうかをユーザーに聞かない**: 重さで決まる。low を直さなかったことは、ステップの報告に一行で添える。
- **重さは監督役が確かめる**: レビュアーが付けた重さを、根拠を読んで確かめる。過大・過小なら付け直し、付け直したことを報告に書く。
- low まで直そうとすると、レビューのループが収束せず、差分も膨らむ。

## 方針が分かれたとき

- 設計の論点、指摘の直し方、設計から外れる判断など、対応の方針が分かれたら、**推奨する案で進める。ユーザーに判断を仰がない。**
- 選んだ案は、選択肢と理由を添えて記録する（設計書の「決定事項」、`response-r<K>.md`、コミットメッセージ）。ステップの報告で、推奨で決めた方針としてユーザーに伝える。ユーザーが別の案を望んだら、そこで切り替える。
- 次は方針の選択ではないので、これまでどおりユーザーに確認する。
  - 依頼の範囲を広げる変更（README、CI、頼まれていない機能など）
  - 要件を変える判断（下の基準を参照）
  - SKILL.md の「締め」で明示の指示を求めている操作と、破壊的な操作

### 要件を変える判断の基準

- **要件を変える判断**は、採用すると合意済みの目的・完了条件・対応範囲が変わるか、満たせなくなる判断を指す。issue、合意済みの仕様、ユーザーの指示から該当する記述を引き、対象ケースに適用される理由と、採用時に満たせなくなる振る舞いを示す。対象環境を狭める場合も同じ基準で扱う。
- **方針の選択**: 完了条件で決まっていない細部の振る舞いは、ユーザーに見える振る舞いであっても方針の選択として扱う。たとえば次のもの。
  - 表示の出し方や消えるタイミングなど、UI の細かい振る舞い
  - エッジケースやエラーのときの扱い
  - 前提の機能が無効な環境や対応外の環境での振る舞い（そのまま許容するか、画面で知らせるか）
- 要件の適用範囲や実現可否が曖昧なら、先に資料や実行結果で確かめる。要件を満たせるかを左右する不明点が残ったら、そこに絞ってユーザーに聞く。

## 監督役の仕事

- **ブリーフを書く**: サブエージェントはこの会話を知らないので、渡したブリーフがすべてになる。書くことは下の「ブリーフに書くこと」を参照。
- **報告を鵜呑みにしない**: サブエージェントの報告は、あくまで本人の自己申告。成果物のファイル、`git log origin/main..<branch>`、`git show` を自分で読んで確かめてから、ユーザーに伝える。
- **ユーザーとのやりとりを一手に引き受ける**: サブエージェントが報告で質問や判断待ちを返してきたら、方針の選択なら監督役が推奨で決める。ユーザーに聞く論点は、次の手順で確かめる。答えは、そのサブエージェントへの続きの依頼として渡す。
- **ユーザーに聞く前に分類を確かめる**: 設計書の未決事項や、サブエージェントが「ユーザーに聞きたいこと」として返した点は、サブエージェントの分類のままユーザーに聞かない。1 件ずつ次を行う。
  1. 「要件を変える判断の基準」に照らし、該当する要件と対象ケースへの適用範囲を確かめる。
  2. 現行の要件を満たす案があれば、その中から推奨案を選ぶ。設計エージェントに「決定事項」の章へ移させ、採った案と理由を報告する。
  3. 依頼範囲や要件の変更が必要なら、変更する要件や範囲、具体的な影響、選択肢、推奨と理由を添えて聞く。要件を満たせるかを左右する不明点は、解消に必要な情報を聞く。
- **ユーザーに短く伝える**: ステップが終わるたびに、判定、medium 以上の指摘の要点、推奨で決めた方針、起票した別件のチケット、次に何をするかを伝える。ループの経過（r1 は要修正、r2 は要修正、r3 は OK）は表にする。
- **範囲の判断はユーザーに返す**: README など頼まれていない変更と、要件を変える判断は、ユーザーに決めてもらう。方針の選択は「方針が分かれたとき」に従う。
- **本筋以外は起票する**: 途中で見つかった別の問題は、その場で深追いせず、SKILL.md の「本筋以外の発見」に従って起票する。すぐに調査が必要なものだけ、別セッションの提案として切り出す。

## 成果物の置き場と名前

設計の成果物は、監督役の作業フォルダに作る未追跡の `design/` に置く。コミットはしない。残す価値のある判断は、PR 本文に書き写す。

| ファイル | 書く人 |
|---|---|
| `design/issue-<N>-<短い英語名>.md` | 設計エージェント（設計書） |
| `design/issue-<N>-review-r<K>.md` | レビューエージェント（K 回目のレビュー） |
| `design/issue-<N>-response-r<K>.md` | 設計エージェント（r<K> の指摘への対応） |
| `design/issue-<N>-review-independent.md` | 独立レビューのエージェント |
| `design/issue-<N>-impl-review-r<K>.md` | 実装レビューのエージェント |

実装エージェントは別の worktree で動くので、`design/` は絶対パスで読ませる。実装エージェントには `design/` をコピーさせず、コミットにも含めさせない。

## ブリーフに書くこと

どのサブエージェントにも、次を書く。
- **目的**: 何をして、何を判定するか（一文で）。
- **最初に読む migiude のファイル**: サブエージェントは監督役が読み込んだスキルを引き継がないので、絶対パスで渡す。スキルの置き場はエージェントによって違うので、監督役が読み込んだ migiude のディレクトリを基準にする。どのステップでも `SKILL.md` を読ませる。加えて、担当に合う reference を読ませる。
  - 設計: `references/design-docs.md`
  - レビュー（設計・実装）: `references/review.md`
  - 実装: `references/implement.md`
  - 文章を書くステップ（設計書、レビュー、コミット）: `references/writing.md`
- **読むもの**: issue（`gh issue view <N>`）、リポジトリのエージェント向けの指示ファイル（`CLAUDE.md`、`AGENTS.md` など）、関係するコード、前のステップの成果物（絶対パスで）。
- **成果物**: どのファイルに、どんな形式で書くか。
- **制約**
  - 成果物のファイル以外は変更しない。
  - commit・push・PR・issue の起票やコメントはしない（実装エージェントのコミットだけは例外）。本筋以外の発見は、最終報告に別件として分けて書く。
  - 実験は `$TMPDIR` で行う。
  - 推測で断定せず、確かめられないことは「未確認」と書く。
- **ユーザーが決めたこと**: 設計の決定事項。蒸し返さないよう、前提として渡す。
- **判断に迷ったとき**: 方針が分かれたら推奨する案で進め、選択肢と理由を成果物と報告に残すこと。範囲を広げる判断、要件を変える判断、要件を満たせるかを左右する未確認事項は、根拠とともに報告すること。サブエージェントはユーザーに直接聞けないので、ここを書いておかないと、止まるべき点まで推測で決めてしまう。あわせて「要件を変える判断の基準」の節をそのまま写して渡す。基準を渡さないと、完了条件で決まっていない細部まで要件として返ってくる。
- **最終報告の形**: 何を報告して終わるか（判定、指摘の要点、変更したファイル、コミットの一覧、未確認のこと、推奨で決めた方針、ユーザーの判断が必要な点、別件として見つけたこととその根拠）。
- **背景**: プロダクトの概要、この issue の位置づけ、今どのステップにいるか。

## 設計

- 設計書には、少なくとも次を書く。
  - 層と型の配置
  - 公開 API のシグネチャ
  - 並行処理の方針
  - 外部仕様（出典付き）
  - エラーの扱い
  - 状態と遷移
  - テスト計画（ケースの一覧）
  - コミットの分割案
  - 決定事項（分かれた方針ごとに、選択肢、採った案、理由）
  - 未決事項（依頼範囲・要件の変更や、要件を満たせるかを左右する未確認事項。判断の根拠と影響を添える）
- 方針が分かれる点は、設計エージェントが推奨する案で決め、「決定事項」の章に書く。完了条件で決まっていない細部の振る舞いもここに入る。レビューで別の案のほうが良いと分かれば、そこで変える。
- 未決事項は監督役に返す。監督役は「ユーザーに聞く前に分類を確かめる」の手順に従い、決まった内容を「決定事項」の章へ移させる。

## 設計レビュー

- レビューの冒頭に判定を書く。**OK**（設計上の要修正事項が解消した）か**要修正**か。
- 指摘ごとに、重さ（high / medium / low。「指摘の重さと対応」を参照）、章番号、問題、根拠（file:line、ドキュメント、実験の結果）、直し方の案を書く。**medium 以上が 1 つでもあれば要修正**にする。
- 2 回目以降は、前回の指摘ごとの解消状況を表にする。別案で対応されたものと不採用になったものは、その理由が成り立つかを確かめる。設計者の理由のほうが正しければ受け入れる。
- 設計書の技術的な主張は、公式ドキュメントや `$TMPDIR` での小さな実験で裏を取る。実験でしか見つからない問題（失敗の経路で処理が止まる、後始末が抜けてループが回り続ける、など）がある。

## 再設計

- レビューの指摘をそのまま採らない。指摘ごとに、今の実装、公式ドキュメント、ベストプラクティス、デザインパターンに照らして検討し直す。レビューの直し方の案より良い設計があれば、そちらを採る。
- `response-r<K>.md` に、指摘ごとの対応（採用 / 別案で対応 / 不採用）、理由と根拠、設計書のどこを変えたか（章番号）を書く。
- 指摘を 1 つ直したら、その修正が既存の手順と矛盾しないかを、該当する章全体を通して見直す。

## 独立レビュー

- 新しいサブエージェントで行う。**自分の判定を書き終えるまで、過去のレビューと対応のファイルは読ませない。**
- 判定を書いた後で過去のレビューを読ませ、重なりや見解の違いを「過去のレビューとの照合」の節に書かせる。
- 要修正だった場合は、設計エージェントに直させ、この独立レビュアーに再レビューさせる。

## 実装

- 実装エージェントは、専用の worktree で動かす。エージェントに worktree を分けて動かす機能があればそれを使い、なければ監督役が `git worktree add` で作ってパスを渡す。最初に、`origin/main` の最新から、SKILL.md の「準備」に従った名前のブランチを切らせる。
- 設計書のコミット分割案に沿って、作業単位でコミットする。各コミットの前に、リポジトリが定める lint とテストを通す。
- 設計レビューで残った low の指摘には対応させない。
- 設計から外れる判断が必要になったら、推奨する案で進めさせ、外れた点と理由をコミットメッセージと報告に書かせる。ユーザーの判断が必要な点は「方針が分かれたとき」の基準に従って監督役へ返させる。
- 作業ブランチの push と PR 作成は、実装レビューの後に監督役が担当する。

## 実装レビューと修正

- 新しいサブエージェントで、ブランチの差分（`git diff origin/main...<branch>`）を設計書と突き合わせる。
- 直すのは medium 以上の指摘だけ。ユーザーに確認せずに直させる。
- 修正は、実装エージェントに続きとして頼み、**追加のコミット**として積ませる。既存のコミットは書き換えない。

## 検証の分担

- サンドボックスでは、テストの一部（自前のサンドボックスを使うビルドツール、システムの一時ディレクトリに書くツールなど）が実行できないことがある。その場合、サブエージェントには代わりの方法で確かめた範囲を報告させる。監督役は、ユーザーに実行してもらうコマンドをコピーしてそのまま動く形で渡す。
- 渡すコマンドには `; echo "exit=$?"` を付け、終了コードまで確かめる。出力を抑えるオプションを付けたコマンドでは、「失敗の出力がない」ことが成功を意味しない。
- 既存テストが失敗したときは、[実装手順の「テスト」](implement.md#テスト) に従う。

## PR と片付け

- 実装レビューで OK が出たら、監督役が [review.md](review.md) の手順で作業ブランチを push し、対応する PR がなければ作成する。
- PR 本文は、リポジトリの過去の PR と同じ構成にする。`Closes #<N>` を入れる。issue と関係のない修正を取り込んだ場合は、「その他の変更」として分けて書く。
- マージ後は、ローカルの `main` を `origin/main` に fast-forward する。比較や派生の基準には、ローカルの `main` ではなく `origin/main` を使う（ローカルの `main` は古いことがある）。
- マージを確かめたら、ユーザーに確認せずに片付ける。
  - 片付けるもの: マージ済みのブランチ（ローカルとリモート）、実装用の worktree、確認のために作った一時的なリポジトリやファイル、`design/`。
  - `design/` を消す前に、残す価値のある判断が PR 本文に移っていることを確かめる。
  - 片付けないもの: マージされていないコミットや未追跡の変更が残っているもの、ほかのセッションの worktree。見つけたら、消さずにユーザーに伝える。
  - 監督役のセッションが動いている worktree は、中からは消せない。セッションのアーカイブのときに片付けてもらうよう、ユーザーに伝える。
