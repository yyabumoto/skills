# 文章の作法（コメント・コミット・PR・文書・報告）

## 共通

- 日本語、常体で書く。リポジトリの慣習が英語なら、コードのコメントだけはそれに合わせる。
- **経緯・日付・タスク ID・進捗を本文に書かない**。「今日」「現時点で」「〜を削除した」「もう〜はない」も書かない。git の履歴で追えることは git に任せ、文書には現在の状態だけを書く。
- 用語を統一する。プロジェクトで使われている呼び名に合わせ、途中で言い換えない。
- 造語・比喩・社内でしか通じない略語を使わない（「錨」「壁」「段4」のような語は伝わらない）。抽象語（「契約」など）を使うなら定義を置く。非エンジニアが読むなら略語を開く。
- 強い言い回しや過剰な強調を避ける。注意書きは必要なものだけ。
- 何に対する判断・根拠なのかが分かるように書く。比較の形ではなく「その案で何が良くなるか」で書く。
- 省略しない。「他も同様」で済ませず、必要なものは全部載せる。

## コード中のコメント

- 原則: **コードに How、テストに What、コミットに Why、コメントに Why not**。コメントは「なぜこう書いたか」がコードから読み取れないときだけ書く。
- 書かないもの: コードを読めば分かる What、ユーザーから受けた指示、検討して捨てた案の経緯、タスク ID、変更履歴、存在しない箇所への言及、ライブラリ内部の実装の説明。
- 仕様の説明はコメントではなく仕様書に書く。
- 周囲のコードのコメント量と書き方に合わせる。Dockerfile や Makefile のように短いファイルに長い説明を書かない。

## コミットメッセージ

- [Conventional Commits](https://www.conventionalcommits.org) に従う。type（`feat` `fix` など）と scope は英語、タイトルと本文は日本語で書く。例: `feat(auth): パスワード再設定の導線を追加する`
- 何を変えたかより、なぜ変えたかを書く。
- 1 コミット 1 目的。

## PR 本文

- テンプレートがあれば従う。粒度は同じリポジトリの他の PR に合わせる。
- 「なぜ」と判断の根拠（調査結果やデータへのリンク）を書く。「確認方法」は箇条書きで、実際に行った確認だけを書く。
- 件数や日付のように変わる情報は書かない。
- 本文を更新するときは、ユーザーが手で直した箇所を壊さない。

## 報告（チャット・レポート）

- 結論を先に書く。次に根拠（file:line、実行結果、データ）、未確認事項、ユーザーに判断してほしいこと、の順。
- ユーザーに選んでもらう論点は、選択肢に記号を振り、推奨を添える。
- ユーザーがすべきこと（実行してほしいコマンド、判断してほしい点、確認すべき点）は分けて明示する。
- 監督モードのサブエージェントの報告で「判断してほしいこと」に挙げるのは、依頼範囲・要件の変更や、要件を満たせるかを左右する未確認事項。方針の選択は、推奨で決めた方針として書く（[orchestrate.md](orchestrate.md) の「方針が分かれたとき」）。
