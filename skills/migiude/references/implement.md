# 実装（機能追加・修正・リファクタ・バージョンアップ）

## 手順

1. **要件の確認**: 背景、やること、やらないことを短く言い直す。言語・技術の指定（TS か JS か、ネイティブか Web か等）を取り違えない。不明点は資料や実行結果で確かめ、要件を満たせるかを左右するものが残ったら聞く。
   - 監督モードの実装エージェントは、ユーザーに直接聞けない。不明点は、まず設計書と issue の完了条件で確かめる。それでも決まっていない点は、[orchestrate.md](orchestrate.md) の「要件を変える判断の基準」に照らす。方針の選択なら推奨する案で進め、選んだ案と理由をコミットメッセージと報告に書く。ユーザーの判断が必要な点は、報告で監督役に返す。
2. **既存実装を読む**: 変更箇所と、同種の処理が他でどう書かれているかを確認する（file:line）。
3. **方針を出す**: 大きい・迷う変更では、採用する方針と理由をブランチを切る前に伝える。ユーザーに選んでもらう論点は SKILL.md の「方針提示」に従う。小さく自明な変更ならそのまま進めてよい。
   - 監督モードの実装エージェントは、方針を出し直さずに設計書に従う。設計から外れる判断が要るときは、[orchestrate.md](orchestrate.md) の「実装」の節に従う。
4. **ブランチを切る**: SKILL.md の「準備」に従う。
5. **実装する**: 最小スコープ、既存の流儀、単純さを守る。コメントは [writing.md](writing.md) のルールに従う（why だけ）。
6. **自己検証**: lint / format / 型 / 該当テスト / ビルド / 実際の動作確認を自分で実行し、結果を示す。失敗は原因を調べて対処する。既存テストの失敗は「テスト」の節に従う。検証のコマンドには `; echo "exit=$?"` を付けて終了コードまで示す。出力を抑えるオプションを付けると、失敗の出力がないことは成功を意味しない。
7. **コミット計画**: 変更が複数の意味を含むなら、コミットの分け方を挙げて承認を得てからコミットする。
   - 監督モードの実装エージェントは、承認を待たずに設計書のコミット分割案に沿ってコミットする。分割案から外れたら、外れた点と理由を報告に書く。
8. **push・PR 作成**: 「締め」に従い、[review.md](review.md) の手順で進める。監督モードでは監督役が担当する。

## 規模が大きいとき

- 実装計画を文書にし、タスクを 1 タスク 1 ファイル・1 タスク 1 ブランチに分ける。タスク番号は着手順を意味しない。
- 複数ブランチにまたがるなら、統合ブランチを切ってそこからタスクブランチを切る、または stacked PR にする。どちらにするかはユーザーに確認する。

## テスト

- テストを書くよう頼まれたら、指定された範囲だけ書く（「U-3 のテストだけ」なら U-3 だけ）。
- 既存テストを、既存仕様を守りデグレを検知する基準として扱う。失敗したら変更前のコードでも同じテストを実行し、どの振る舞いを保証しているかを仕様と照合する。
  - テストが仕様どおりで、実装に不具合があれば実装を直す。
  - テスト自体に問題があり、期待する振る舞いとデグレを検知する範囲を維持できるなら、エージェントの判断でテストを直し、同じ PR に含める。
  - テストを変えると期待する振る舞いが変わる、またはこれまで検知できたデグレを見逃す場合は、影響を具体的に示し、変更前に開発者の判断を仰ぐ。実装エージェントは監督役を通じて相談する。
- 変更前から失敗していた分の修正は別コミットに分け、PR 本文の「その他の変更」に書く。
- テストを書きやすくするためだけに、実装の設計を変えない。

## バージョンアップ・依存更新

- 変更点（changelog、移行ガイド）を一次資料で確認してから、影響箇所を洗い出す。
- 非互換の箇所は静的解析とテストで確かめる。機械的な一括置換で済ませず、意味が変わる箇所を個別に見る。

## よくある失敗

- 認証方式を使ってほしかっただけなのに、その方式の実装を作り込む → 依頼の動詞（使う／作る／調べる）を確認する。
- 指定していない API・ライブラリ・構成を持ち込む → 選ぶ前に聞くか、既存に合わせる。監督モードの実装エージェントは、設計書にあるものを使い、なければ既存に合わせる。新しく持ち込む必要があるなら、設計から外れる判断として扱う（[orchestrate.md](orchestrate.md) の「実装」の節）。
- 無関係な変更（別タスクの差分、生成物）をコミットに巻き込む → コミット前に `git status` と差分を確認する。
