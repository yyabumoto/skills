# 設計・文書（設計相談、仕様書、実装計画）

## 設計相談

1. **意思決定の木を作る**: 決めるべき論点を洗い出し、依存関係の順に並べる。
2. **論点ごとに決める**: [orchestrate.md](orchestrate.md) の「方針が分かれたとき」に従って、採った案と理由を記録して伝える。ユーザーの判断が必要な論点や、ユーザーが自分で決めたいと指定した論点は、選択肢と推奨を示して一問ずつ決定を待つ。
3. **決まったこと／検討中／担当** を分けて記録する。監督モードで設計書の未決事項に残す内容は、[orchestrate.md](orchestrate.md#設計) の「設計」に従う。
4. **独立した反証**: 重要な設計は、別のエージェントやセッションに反証させてから確定する。
5. 目的に関係しない観点（比較基準、順序、依存のない項目）を混ぜない。採用しなかった案は、求められない限り書かない。

## 文書の作り方

1. **骨組みから**: まず見出し（章立て）だけを作って合意を取る。「今は土台だけ」の段階で中身を埋めすぎない。監督モードの設計書は、章立ての合意を待たずに [orchestrate.md](orchestrate.md) の「設計」の節の章立てで書き切る。
2. **セクションごとに埋める**: 一節ずつ書き、必要ならその節の論点を詰めてから次へ。
3. **レビューを受ける**: ユーザーのコメントを全件反映する。行単位の指摘は該当箇所だけ直す。
4. **仕上げ**: 全体の整合（用語、前後の矛盾、古い記述）を確認する。追記を重ねて継ぎはぎになっているなら書き直す。

## 文書の種類ごとの注意

- **要求定義・API 仕様**: 実装の都合（内部のテーブル名、使うライブラリ）を書かない。外から見た振る舞いだけを書く。
- **実装計画・QA 方針**: タスクの粒度と完了条件を揃える。読み手（アプリ担当、インフラ担当、非エンジニア）に合わせて詳しさを変える。

文章そのものの作法（経緯を書かない、用語、常体など）は [writing.md](writing.md) に従う。
